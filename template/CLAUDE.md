# Règles de ce projet (générées par le skill starter-saas)

- **PAGE DE PAIEMENT VERROUILLÉE (OBLIGATOIRE)** : la fenêtre de paiement (`CheckoutModal`), ses moyens (Mobile Money, Wave, carte, PayPal, crypto Binance / USDT TRC20), leur disposition et tout le circuit d'une commande (passerelles, webhooks, vérification, livraison, facture) sont une brique COMMUNE à tous les SaaS du kit. Les fichiers listés dans `paiement.lock.json` ne se modifient JAMAIS dans un projet : `npm run lint`, `npm run build` et la CI échouent sinon (`scripts/verrou-paiement.mjs`). Jamais `--signer` ici. On règle : `site.ts` (nom, logo, WhatsApp, pays par défaut), `/admin/keys` (Tara Money, Warappay, Wave, Binance, USDT), `/admin/payment-providers` (passerelle active par moyen), `/admin/products` (produits et prix). Une amélioration utile à tous se fait dans le kit, puis la brique est réinstallée.
- **Branding et textes** : `src/config/site.ts` (nom, personne, logo, accroche, « À propos », FAQ, réseaux, WhatsApp, fuseau, menus). **Produits, prix, formations et leçons : en base** (`products`, `lessons`), réglés dans `/admin/products`, jamais dans le code.
- **Modules** : `site.modules` dans `src/config/site.ts` allume ou coupe chaque brique (formations, boutique, communauté, appels, avis, demandes, crédits). Un module coupé disparaît des menus et de l'accueil, et ses pages répondent « introuvable » (`requireModule()` de `src/lib/modules.ts`, à appeler en tête de toute nouvelle page d'un module).
- **Types de SaaS** : formation / cours en ligne (catégories `formation`, `accompagnement`, `abonnement`), boutique de produits numériques et services (`logiciel`, `service`, fichiers privés), SaaS à l'usage (`credits` : packs de crédits, `debitCredits()` avant chaque action payante). Tout passe par la même page de paiement et la même livraison (`credit_paid_order`).
- **Accès aux contenus** : uniquement par `entitlements` (fonctions SQL `credit_paid_order` / `grant_product_access`). Vidéos et fichiers dans le stockage PRIVÉ (`videos`, `files`, `community`), lus par lien signé court.
- **Charte graphique** : couleur de marque = `--brand` / `--brand-dim` dans `:root` de `src/app/globals.css` (le bloc `@theme` en dérive `bg-brand`, `text-brand`, `hover:bg-brand-hover`) ; police = `src/app/fonts/brand-font.ts` (+ les mêmes fichiers dans `public/fonts` pour les factures PDF) ; logo = `site.logo` ; icône = `src/app/icon.png`. Les pages publiques ont des styles en ligne avec les variables de la charte (`var(--brand)`, `var(--white)`, `var(--black-card)`…) : c'est voulu. Jamais de couleur en dur dans un composant.
- **Interface 100 % aux couleurs du site (OBLIGATOIRE)** : AUCUN élément natif du navigateur. Interdits : `<select>`, `<input type="date|time|radio|checkbox|color|range">`, `confirm()`, `alert()`, `prompt()`, `window.open`, `<dialog>` brut, infobulles `title`. Utiliser `src/components/ui` : `Select`, `DatePicker`, `RadioCard`, `Checkbox`, `Switch`, `useConfirm`, `PhoneInput` ; messages d'erreur et de succès DANS la page. `npm run lint` bloque ces éléments.
- **Champs de réglage** : toute fenêtre qui modifie une valeur existante (clés, réglages, fiches) s'ouvre PRÉ-REMPLIE avec la valeur en place (ou la valeur par défaut du code), visible (œil pour un secret) et modifiable directement ; seuls les champs changés sont enregistrés. Jamais un champ vide « laisser vide pour garder ».
- **Clés de services** (paiement, Brevo, CRON_SECRET, IA) : collées par le propriétaire dans `/admin/keys` ; toute nouvelle clé se déclare dans `src/lib/secrets/catalog.ts` (avec `defaultValue` si le code en a une) et son service dans `src/lib/secrets/services.ts` avec son logo officiel.
- **Menus** : espace client = `site.dashboardNav` (avec `module` si la page appartient à un module) ; administration = `NAV` de `src/app/admin/AdminNav.tsx` et réglages dans `AdminTopBar.tsx`.
- **Authentification** : Supabase. Déconnexion = `POST /auth/signout` (`LogoutButton`). Pages privées protégées par `src/middleware.ts` ET revérifiées côté serveur avec `getUser()`. Validation en deux étapes (e-mail ou application) et connexion Google (clés dans `/admin/keys`).
- **Administration** : `/admin`, réservé à `profiles.is_admin = true` (premier compte créé par l'assistant `/setup`).
- **E-mails** : `sendEmail` / `sendEmailDetailed` (`lib/email/brevo.ts`) notent chaque envoi dans `email_log` (Administration › E-mails). Jamais de code ni de secret dans le SUJET. Tout nouveau modèle se déclare dans `EMAIL_EXAMPLES` (`lib/email/templates.ts`).
- **Heures** : créneaux d'appel, fins de promo et statistiques à l'heure de `site.timezone` (`src/lib/time.ts`), jamais un décalage écrit en dur.
- **Base de données** : Supabase OPEN SOURCE hébergé par le créateur (Docker en local, service Coolify `api.<domaine>` en ligne). JAMAIS de compte supabase.com. Installation : `/setup` (local) et `/admin/deploy` (en ligne).
- **Migrations** : uniquement dans `supabase/migrations/` : un fichier NEUF par changement (`AAAAMMJJHHMMSS_nom.sql`, numéro UNIQUE), jamais de modification d'une migration déjà appliquée. Toujours rejouables (`if not exists`, `drop policy if exists`), RLS activée sur chaque table, index sur chaque clé étrangère. Le catalogue d'exemple (`20261011000100_catalogue_exemple.sql`) se remplace dans l'admin, pas dans une migration.
- **Robustesse** : chaque appel extérieur a un délai maximal (`AbortSignal.timeout(15_000)`), chaque écriture en base lit son `{ error }`, chaque liste qui grandit est paginée.
- **Secrets** : jamais dans Git ni dans le chat. `.env.local` en local, variables d'environnement de l'hébergeur en production.
- **Vérifier avant de livrer** : `npx tsc --noEmit`, `npm run lint` (verrou de paiement compris), `npm run build`, puis essai réel dans le navigateur (inscription → connexion → achat → déconnexion).
